# قاعدة البيانات

## الهجرات بالترتيب

| الملف | ماذا يضيف |
| --- | --- |
| `01_stories_and_admin.sql` | الأدوار و `is_admin()` و `profiles` و `success_stories` والتخزين |
| `02_story_amount.sql` | حقل المبلغ على بطاقة قصة النجاح |
| `03_members.sql` | بيانات الأعضاء: البريد ورقم العضوية والباقة |
| `04_closed_membership.sql` | عضوية مغلقة، وصلاحيات على مستوى الأعمدة، و `has_active_subscription()` |
| `05_content_and_classes.sql` | المستويات والدروس والاختبارات والحصص والحجوزات |

شغّلها بالترتيب، وكلها آمنة لإعادة التشغيل.

## التشغيل

افتح مشروع Supabase ← **SQL Editor** ← **New query**، ثم شغّل الملفات بالترتيب:

1. `01_stories_and_admin.sql` — الأدوار والقصص والتخزين والسياسات.
2. `02_story_amount.sql` — حقل المبلغ على بطاقة القصة.

قبل ذلك تأكد أن حساب الإدارة موجود في **Authentication → Users**.
الجزء الخامس من السكربت يتوقف بخطأ واضح إذا لم يجد البريد، ولا ينشئ دوراً معلّقاً.

## ما ينشئه السكربت

| العنصر | الغرض |
| --- | --- |
| `user_roles` | الدور الإداري، منفصل عن `profiles` حتى لا يرقّي المستخدم نفسه |
| `is_admin()` | دالة `security definer` تستخدمها كل السياسات |
| `profiles` | بيانات المستخدم، تُنشأ تلقائياً عند التسجيل |
| `success_stories` | القصص: عنوان، نص، اسم المتدرب، صورة، ترتيب، حالة نشر |
| `story-images` | مجلد التخزين، صور فقط وبحد أقصى 3 ميغابايت |

## المحتوى والحصص (الهجرة الخامسة)

- **المستويات** و**جدول الحصص** المنشوران يقرأهما الزائر.
- **الدروس**: المنشور يقرأه المشترك النافذ اشتراكه فقط، إلا ما عُلِّم
  `free_preview` فيقرأه الزائر — وهذه العيّنة المجانية هي الفرق الوحيد.
- **الاختبارات**: جدولا `questions` و `answers` لا يُقرآن من الـ API إلا للإدارة.
  المشترك يأخذ الورقة من `quiz_paper()` وهي **لا تُرجع الإجابة الصحيحة**،
  والتصحيح في `grade_quiz()` داخل القاعدة. فلا تُكشف الإجابات من أدوات المطور.
- **الحجز**: لنفسه فقط، باشتراك نافذ، على حصة منشورة مجدولة لم يبدأ موعدها.
  والسعة مفروضة بمشغّل `enforce_slot_capacity` لا بفحص في الواجهة.

## نموذج الصلاحيات

- **الزائر**: يقرأ القصص المنشورة فقط. المسودات لا تخرج من قاعدة البيانات.
- **المستخدم المسجّل**: يقرأ ملفه ودوره فقط. لا يستطيع إضافة أو تعديل أو حذف أي قصة، ولا رفع صورة.
- **الأدمن**: يقرأ كل القصص ويضيف ويعدّل ويحذف ويرفع الصور.
- **لا أحد** يستطيع تغيير الأدوار عبر الـ API. جدول `user_roles` بلا سياسة كتابة إطلاقاً،
  فمنح الصلاحية يتم من SQL Editor فقط.

الحماية كلها في قاعدة البيانات لا في الواجهة. حتى لو استدعى أحدهم الـ API مباشرة
بمفتاح `anon`، سياسات RLS ترفض الطلب.

## المفاتيح

الواجهة تحتاج **anon / publishable key** فقط، وهو مصمَّم ليكون علنياً في المتصفح.
مفتاح `service_role` لا يوضع في الواجهة ولا في هذا المستودع إطلاقاً.

## ترتيب التشغيل

```
01_stories_and_admin.sql
02_story_amount.sql
03_members.sql
04_closed_membership.sql
05_content_and_classes.sql     ← المستويات والدروس والاختبارات والحصص
05_roles_and_profile.sql       ← الأدوار وحماية حقول الملف الشخصي
07_content_tree.sql            ← المسارات والدورات والمفردات والتصحيح الآمن
```

ملفان يحملان الرقم 05 لأنهما كُتبا بالتوازي. لا يتعارضان: الأول للمحتوى
والثاني للأدوار. شغّلهما بأي ترتيب بينهما، ثم `07`.

## أمان الاختبارات

جدولا `questions` و `answers` مقصوران على الإدارة بسياسات RLS، فلا يصل
إليهما المتعلم إطلاقاً. طريقه الوحيد دالتان:

- `get_quiz(id)` تُرجع الأسئلة والخيارات **بلا عمود `is_correct`**.
- `submit_quiz(id, answers)` تصحّح على الخادم وتحفظ المحاولة وتعيد النتيجة.

فحتى لو فتح المتعلم أدوات المطور وقرأ كل ما وصل إلى المتصفح، لا توجد
فيه إجابة صحيحة واحدة.
