## 2. نقطة الربط الوحيدة في الواجهة

كل منطق النماذج في `assets/auth.js`، ونقطة الاستبدال **دالة واحدة**:

```js
function submitToApi(payload) { /* ... */ }
```

تستقبل `{kind, email, password, name}` حيث `kind` إما `login` أو `signup` أو `reset`،
وتُرجع `Promise` بـ `{ ok: true }` أو `{ ok: false, field?: 'email', message: '...' }`.

استبدلها باستدعاء Supabase Auth الفعلي. **لا تغيّر** بقية الملف: التحقق من المدخلات
ورسائل الخطأ العربية وحالات التحميل ومنع الإرسال المتكرر كلها جاهزة ومختبرة.

احذف عند الربط: الثابتين `DEMO_EMAIL` و `DEMO_PASSWORD`، ودالتي
`registeredEmails` و `rememberEmail`، وبطاقة الحساب التجريبي في `login.html`.

## 3. قاعدة البيانات

السكربت جاهز في **`supabase/01_stories_and_admin.sql`** — شغّله من SQL Editor.
يغطي: جدول الأدوار، دالة `is_admin()`، جدول `profiles`، جدول `success_stories`،
مجلد التخزين، و13 سياسة RLS. تفاصيله في `supabase/README.md`.

### قرارات تصميم مقصودة، لا تنقضها

1. **الدور في جدول `user_roles` منفصل، لا كعمود في `profiles`.**
   لو كان عموداً في الملف الشخصي لأمكن المستخدم ترقية نفسه وهو يعدّل اسمه.
2. **`user_roles` بلا أي سياسة كتابة.** مع تفعيل RLS = منع كامل عبر الـ API.
   منح الصلاحية من SQL Editor فقط.
3. **المسودات لا تخرج من قاعدة البيانات.** سياسة الزائر `using (published = true)`،
   فلا تظهر المسودة حتى لو استُدعي الـ API مباشرة. لا تكتفِ بإخفائها في الواجهة.
4. **`is_admin()` بصلاحية `security definer` و `search_path` مثبّت** ضد حقن الدوال.

### ما نُفِّذ بعد ذلك

`03_members.sql` بيانات الأعضاء · `04_closed_membership.sql` العضوية المغلقة
وبوابة الاشتراك · `05_content_and_classes.sql` جداول
`levels` · `lessons` · `quizzes` · `questions` · `answers` ·
`class_slots` · `bookings` بسياساتها.

النمط نفسه مطبَّق عليها: RLS مفعّل، قراءة عامة للمنشور فقط، والكتابة لـ `is_admin()`،
والمحتوى المدفوع مقيَّد بـ `has_active_subscription()` لا بمجرد تسجيل الدخول.

### الباقي بعد

`plans` و `subscriptions` كجدولين مستقلين — حالياً الاشتراك حقول في `profiles`،
وتفصيله ينتظر حسم ربط سلة في القسم 5 أدناه.

## 4. لوحة الإدارة

صفحات عربية RTL بهوية نورث. استخدم `assets/app.css` فالتوكنات والمكوّنات جاهزة.

**الأولوية الأولى: قصص النجاح.** نفّذها واختبرها واعتمدها قبل البقية.

### إدارة قصص النجاح

قائمة تعرض: صورة مصغرة، العنوان، حالة النشر، تاريخ آخر تعديل، وأزرار تعديل وحذف
وتبديل النشر. مع حالات: قائمة فارغة، جارٍ التحميل، خطأ.

نموذج الإضافة والتعديل: صورة برفع ومعاينة قبل الحفظ، عنوان **مطلوب**، نص القصة،
اسم المتدرب (اختياري) مع مفتاح `show_name`، ترتيب العرض، وحالة النشر.

عند استبدال صورة: احذف القديمة من التخزين حتى لا تتراكم ملفات يتيمة.
عند الحذف: تأكيد قبل التنفيذ، ثم احذف الصورة معها.
التحقق من الملف **على الخادم أيضاً** لا في المتصفح فقط — النوع والحجم مفروضان
في إعدادات المجلد، فلا تعتمد على فحص الواجهة وحده.

### ربط القسم العام

في `index.html` قسم `#stories` فيه ثلاث بطاقات نموذجية ثابتة. استبدلها بجلب من
قاعدة البيانات مرتّباً بـ `sort_order` ثم `created_at`. بنية البطاقة الجاهزة:

```html
<article class="story">
  <div class="story-img"><img src="..." alt="..."></div>
  <div class="story-body">
    <p class="story-eyebrow">...</p>
    <h3>...</h3>
    <p>...</p>
  </div>
  <div class="story-foot"><span class="story-who">...</span></div>
</article>
```

اسم المتدرب يظهر فقط إذا كان `show_name = true`.
وإذا لم توجد قصص منشورة، اعرض حالة فارغة مناسبة بدل قسم مكسور.

### بقية الأقسام

لوحة رئيسية بأرقام فعلية من قاعدة البيانات (لا أرقاماً ثابتة) ·
إدارة المستخدمين (بحث، تفاصيل، حالة الحساب — بلا أي وصول لكلمات المرور) ·
إدارة المسارات والدروس والاختبارات · إدارة الباقات والاشتراكات ·
إدارة الكلاسات والحجوزات.

**المنفَّذ في `admin.html`:** الأعضاء · المستويات · الدروس والاستراتيجيات ·
الاختبارات بأسئلتها وخياراتها · الحصص والحجوزات · قصص النجاح.

## 5. عائق معماري يحتاج قراراً

**التحقق من الدفع.** الدفع يتم في **سلة** لا في Supabase. لا يصح اعتبار الاشتراك
مدفوعاً لأن المستخدم عاد من صفحة الدفع — لا بد من تأكيد من سلة نفسها.

الموقع الحالي ملفات ساكنة على Render، ولا يستقبل webhooks.

**الحل المقترح:** Supabase Edge Function تستقبل webhook من سلة، تتحقق من توقيعه،
ثم تُنشئ أو تجدّد `subscriptions`. يتطلب صلاحية إعداد webhooks في متجر سلة.
ويبقى ربط المشترك بحسابه عبر البريد المستخدم في الطلب، مع معالجة حالة
اختلاف البريد بين سلة والمنصة.

## 6. الأمان — غير قابل للتفاوض

- `service_role` وأي مفتاح سري **لا يدخل الواجهة ولا المستودع**. الواجهة تستخدم
  مفتاح `anon` فقط، وهو مصمَّم ليكون علنياً، والحماية من RLS.
- **لا تعطّل RLS** لتسهيل التطوير، ولا تستخدم سياسة `using (true)` للكتابة.
- كل صلاحية مفروضة في قاعدة البيانات، لا بإخفاء روابط من الواجهة.
- المستخدم العادي لا يضيف ولا يعدّل ولا يحذف قصة، ولا يرفع صورة، ولا يرقّي نفسه.
- العمليات الحساسة (تغيير حالة دفع، إيقاف حساب) تُسجَّل.

## 7. اختبارات القبول

1. دخول الأدمن ووصوله للوحة.
2. **منع المستخدم العادي** من اللوحة، ومن استدعاء عملياتها مباشرة عبر الـ API.
3. إضافة قصة بعنوان ونص وصورة.
4. حفظ مسودة والتأكد أنها لا تظهر للزائر — **اختبرها باستدعاء الـ API بمفتاح
   `anon` بدون جلسة**، لا بالنظر إلى الصفحة فقط.
5. نشر القصة وظهورها.
6. تعديل العنوان والنص والصورة.
7. تغيير الترتيب وانعكاسه.
8. إلغاء النشر واختفاؤها.
9. حذف بعد تأكيد، مع حذف الصورة.
10. رفع ملف غير مسموح ورفضه.
11. محاولة ترقية مستخدم نفسه إلى أدمن عبر الـ API — يجب أن تفشل.
12. الاختبار على الجوال والحاسب.
13. مراجعة السجلات: لا مفاتيح ولا بيانات حساسة مكشوفة.

## 8. ملاحظة على المحتوى

القصص المنشورة يجب أن تكون بموافقة كتابية موثقة من أصحابها، خصوصاً عند عرض
الاسم أو صورة شخصية أو لقطة محادثة — البيانات المالية الشخصية يحكمها نظام حماية
البيانات الشخصية.

وأي نص يَعِد بأرباح أو عوائد يناقض `disclaimer.html` المنشور على الموقع نفسه،
الذي ينص على عدم ضمان أي أرباح وعلى أن النتائج السابقة لا تدل على نتائج مستقبلية.
هذا قرار يخص صاحبة المنصة، ويُحسم قبل إدخال المحتوى.
